# Audit Logging (Baseline CRUD)

This document describes the initial audit logging capability introduced for CRUD operations. It represents the **baseline** required by the Product Plan (Advanced Security & Auditing) and is designed to be incrementally extended (field-level security enforcement, workflow transitions, export, filters).

## 1. What Is Captured
Each successful mutating CRUD operation (INSERT, UPDATE, DELETE) performed through the dynamic entity REST endpoints writes an entry to the `appbana_audit` table in the active datasource.

As of the latest update, **batch inserts (`POST /api/{entity}/batch`) now generate one INSERT audit entry per successfully inserted row** (where the database returned a generated key). Rows without a retrievable generated key (DB/driver limitation) are skipped without failing the batch.

Columns:
- `id` (identity / sequence)
- `ts` (timestamp generated by the database)
- `op` (INSERT | UPDATE | DELETE)
- `entity` (schema/entity name)
- `pk` (primary key value as string)
- `actor` (token value if auth enabled, else `anonymous`)
- `before_json` (JSON of row before mutation, nullable)
- `after_json` (JSON of row after mutation, nullable)
- `changes_json` (JSON map of changed fields -> `[old, new]`, null if no differences detected)

Notes:
- UPDATE captures only modified columns in `changes_json` (compares raw DB row values before vs after).
- INSERT has `before_json=NULL`, DELETE has `after_json=NULL`.
- Batch inserts: diff shows each non-null column transition from `null` to its initial value.
- For now, actor is the raw token (improvement: map to user identity once auth subject model exists).

## 2. Table Creation
The audit table is auto-created alongside existing meta tables by `JdbcManager.ensureMetaTableFor(...)` for all supported dialects (H2, Postgres, MySQL/MariaDB, SQLite, SQL Server, Oracle).

## 3. API Endpoint
A simple query endpoint is available:
```
GET /audit?entity=<name>&pk=<id>&limit=50&offset=0
```
Parameters:
- `entity` (optional) — filter by entity name
- `pk` (optional) — filter by primary key value
- `limit` (default 50, max 500)
- `offset` (default 0)

Response shape:
```json
{
  "rows": [
    {
      "id": 1,
      "ts": "2025-10-01T00:35:12.345Z",
      "op": "INSERT",
      "entity": "customer",
      "pk": "42",
      "actor": "anonymous",
      "before": null,
      "after": { "ID": 42, "FIRSTNAME": "Jane", "LASTNAME": "Doe" },
      "changes": { "FIRSTNAME": [ null, "Jane" ], "LASTNAME": [ null, "Doe" ] }
    }
  ],
  "limit": 50,
  "offset": 0,
  "total": 1,
  "entity": "customer",
  "pk": "42"
}
```

If an internal error occurred while attempting to log (should be rare), a `lastError` field may appear for diagnostic purposes (not persisted; in‑memory state only).

## 4. Example Sequence
```bash
# Insert single row
curl -s -X POST http://localhost:8080/api/customer \
  -H 'Content-Type: application/json' \
  --data '{"firstName":"Alice","lastName":"Lee","age":30}'

# Batch insert (example with 2 rows)
curl -s -X POST http://localhost:8080/api/customer/batch \
  -H 'Content-Type: application/json' \
  --data '[{"firstName":"Bob","lastName":"Jay","age":25},{"firstName":"Cara","lastName":"Yu","age":26}]'

# Update
curl -s -X PUT http://localhost:8080/api/customer/1 \
  -H 'Content-Type: application/json' \
  --data '{"age":31}'

# Delete
curl -s -X DELETE http://localhost:8080/api/customer/1

# Audit trail for one row
curl -s 'http://localhost:8080/audit?entity=customer&pk=1'
```

## 5. Design Decisions / Constraints
- Logging occurs **after** a successful DB operation using a fresh connection; failures are swallowed to avoid impacting primary CRUD latency.
- No explicit transaction spanning CRUD + audit insert (future: optional transactional coupling).
- `changes_json` built by comparing full pre/post row maps; cost acceptable for small row sizes (future optimization: diff only submitted fields for UPDATE with optional DB trigger strategy).
- Column names in `before`/`after` reflect DB column casing produced by metadata-driven table creation (currently uppercase quotes strategy). Frontend / exporter can normalize if needed.
- Batch insert audit intentionally does not wrap the batch transaction again; audit writes occur in a separate auto-commit context after successful insert commit.

## 7. Testing
Integration tests:
- `AuditLogTest` covers single row INSERT→UPDATE→DELETE sequence.
- `BatchAuditLogTest` (new) validates multi-row batch insert logging (one audit row per inserted ID).

## 8. Known Limitations
- No retention policy — audit table can grow indefinitely (future: TTL purge or archive strategy).
- Composite keys unsupported (schema model currently single PK only).
- Batch insert logging relies on JDBC generated keys; some drivers or multi-column PK definitions (future) may not return all keys.

## 9. Next Increment Suggestions
1. Add filtering: `op`, `actor`, `fromTs`, `toTs` query params.
2. Add `export=csv` path producing streaming CSV with consistent column order.
3. Introduce retention config: max days or max rows per entity.
4. Add optional `X-AppBana-Actor` override header for systems using stable user IDs separate from token secrets.
5. Add paging cursor tokens for large audit tables.
